# Addressables Remote Loading Sample

This repository is a Unity sample project for testing remote Addressables content delivery.

The goal is to ship an APK once, then publish new or updated level content through a remote
Addressables catalog and asset bundles hosted on S3. The APK downloads a small remote config,
loads the catalog URL from that config, and then loads levels by Addressables address.

## What This Sample Demonstrates

- Loading an Addressables catalog from a remote URL.
- Hosting Android Addressables catalogs and bundles on S3.
- Loading scene levels from remote bundles without rebuilding the APK.
- Updating available levels by publishing a new catalog and bundles.
- Handling duplicate Addressables locations by reading unique level addresses.
- Preserving engine types needed by future remote content.

## Runtime Flow

1. The app starts in the `Game` scene.
2. `GameManager` initializes the UI and remote config loader.
3. On device builds, remote config is always loaded.
4. In the Unity Editor, remote config is loaded only when `editorAddressablesMode` is set to `Remote`.
5. `RemoteConfigLoader` downloads `config.json`.
6. The current platform catalog URL is read from that config.
7. Addressables loads the remote catalog.
8. `GameManager` reads all unique addresses under the `Level` label.
9. The UI loads levels in the order returned by the sorted address list.

The level list is not generated by guessing `Level_1`, `Level_2`, `Level_3`, etc. It is built from
the actual Addressables locations in the loaded catalog. This avoids showing buttons for levels
that do not exist in the remote catalog.

## Remote Config

Remote config lives on S3:

```json
{
  "android": {
    "catalog_url": "https://terek-addressables-sample-prod.s3.us-east-1.amazonaws.com/staging/Android/v1.1/catalog_0.1.0.bin"
  },
  "ios": {
    "catalog_url": "https://terek-addressables-sample-prod.s3.us-east-1.amazonaws.com/staging/iOS/v1.1/catalog_0.1.0.bin"
  }
}
```

Development builds and Editor remote mode use the staging config.
Non-development player builds use the production config.

## Important Path Rule

The config URL and the Addressables profile load path must point to the same version folder.

For example, if config points to:

```text
staging/Android/v1.1/catalog_0.1.0.bin
```

then the Addressables `Remote.LoadPath` used when building the catalog must also be:

```text
https://terek-addressables-sample-prod.s3.us-east-1.amazonaws.com/staging/[BuildTarget]/v1.1
```

If the config points to `v1.1` but the catalog was built with a `v1.0` load path, Unity will load
the catalog successfully and then try to download bundles from the wrong folder. That causes errors
such as:

```text
RemoteProviderException: Unable to load asset bundle
HTTP/1.1 403 Forbidden
```

After changing `Remote.LoadPath`, rebuild Addressables and upload the new catalog and bundles to
the matching S3 folder.

## S3 Upload Checklist

For each Addressables content release:

1. Set the correct Addressables profile and `Remote.LoadPath`.
2. Build Addressables for Android.
3. Upload the generated catalog, hash, and bundles to the matching S3 folder.
4. Update `config.json` to point to the new catalog.
5. Make sure the uploaded files are publicly readable or otherwise accessible by the app.
6. Clear app/cache data when testing cached catalog or bundle changes.

Useful files usually include:

```text
catalog_*.bin
catalog_*.hash
*_group_scenes_all_*.bundle
```

## Remote Content Compatibility

Addressables can download new asset data, but it cannot add missing Unity engine code to an already
built APK.

Unity can strip engine code during player builds. If `Strip Engine Code` is enabled and the build
does not appear to use a Unity engine type, that type may be removed from the APK. Later, if a remote
bundle contains an asset that needs the stripped type, Unity may fail to deserialize it.

Example warning:

```text
Could not produce class with ID 90
Try disabling 'Strip Engine Code' in Player Settings
```

Unity class ID `90` is `Avatar`. This can happen when a remote bundle contains an Animator or model
Avatar, but the APK build did not preserve Avatar support.

To reduce that risk, this project includes a `RemoteContentCompatibility` object in the build scene
and a prefab at:

```text
Assets/_GameFolders/Prefabs/Compatibility/RemoteContentCompatibility.prefab
```

This prefab intentionally references engine types that remote level content may need, such as:

- Animator
- Avatar
- AnimatorController
- AnimationClip
- MeshRenderer
- MeshFilter
- ParticleSystem
- AudioSource
- TrailRenderer
- LineRenderer
- Light
- Camera

The object is not gameplay content. Its purpose is to make the player build aware of the engine
types that remote content is expected to use.

## Recommended Strategy

For prototyping and development:

```text
Strip Engine Code = Off
```

This is the simplest way to avoid engine type stripping while testing remote content delivery.

For production:

```text
Strip Engine Code = On
RemoteContentCompatibility prefab = maintained intentionally
Remote content rules = documented and enforced
```

Production remote content should only use component and asset types that the APK was built to
support. If a future remote level needs a new engine type that the APK did not preserve, a new APK
build may still be required.

## Known Testing Notes

- Editor local mode can load local Addressables and does not prove remote delivery.
- Editor remote mode and development APK builds use staging remote config.
- Device logs or the in-game development console are the best way to confirm remote bundle failures.
- A catalog can load successfully while an individual bundle still fails if the catalog contains an
  incorrect or inaccessible bundle URL.
